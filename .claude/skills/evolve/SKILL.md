# evolve: 旅行計画アプリ 自動開発サイクル

以下の手順で **1周だけ** 実行してください。
1周 = 「ROADMAP.mdから次に対応する単位(S/M 1〜3個程度)を選ぶ → 実装 → 動作確認 →
簡易セルフレビュー → ドキュメント更新 → commit → push → バックログ更新」です。

---

## 0. 事前チェック
- 作業ブランチは必ず `evolve/cycle-<連番>`。mainにいたら最新化してブランチを作る。
  人間がmainに取り込むまでは、同じブランチに複数サイクル分のコミットが積み重なるのが
  正常な動作である。
- サイクル開始時に `git fetch origin` を実行し、現在のブランチの最新コミットが
  すでに `origin/main` に取り込まれているか確認する。取り込まれていれば
  `git switch main && git pull` で最新化し、新しい `evolve/cycle-<連番+1>` ブランチを
  作り直してから、通常の手順(1節以降)に進む。
- 前回サイクルが未完了(実装済みだがテスト未了、`partial`のまま等)の形跡があれば、
  新しいタスクに着手せず**続きから再開**する。
- ユーザーの手作業らしき変更が混ざっていたら、何もせず報告して終了する。
- `docs/requirements.md`・`docs/screens.md`・`docs/firestore-design.md` を必ず確認し、
  そこで確定した仕様(スコープ・データモデル・セキュリティ方針)から外れた実装をしないこと。

## 1. タスク選定
`docs/ROADMAP.md` を以下の優先順で読み、次に対応するタスクを選ぶ。

1. 「バグ修正(最優先)」セクションの未対応項目
2. `0. 基盤`が未完了なら、他を差し置いて`0. 基盤`のサブタスクを進める
   (全機能がFirestore接続と画面シェルに依存するため)
3. `0. 基盤`完了後は、現在進行中の画面の未完了サブタスク(上から順)
4. 未着手の画面の最初のサブタスク(Must → Should の優先順)

- **サイズLの項目には着手しない**。S/Mの子項目に分割してROADMAPを書き換えるだけで
  1サイクルとしてよい。
- 無関係な複数タスクをまとめる場合も、コミットの差分は項目ごとに分かりやすく分離すること。
  まとめる目安は2〜3項目まで。
- 新しい画面を追加したくなった場合、実装せず`docs/ROADMAP.md`の
  「新規タスク・画面提案」に提案を追記するだけにする(承認制)。
  `docs/screens.md`で決めた画面構成にない画面を勝手に増やさないこと。

## 2. 実装
- 選んだタスクをテスト可能な最小単位で実装する。
- Firestoreへの読み書きは必ず `src/firestore.js` (0章で作成)経由で行い、
  UIのDOM操作コードと混在させない。
- 色は必ず `styles/tokens.css` で定義済みのCSS変数を使う。新しい色が必要になった場合は
  実装せず、その場で確認する。
- `docs/firestore-design.md` のコレクション構造・フィールド名を厳守する。
  スキーマを変えたくなった場合は実装せず、変更案として提案するだけに留める。
- 投票・回答のマップキーに使う「名前」は、Firestoreで使えない文字(`.` `/` 等)を
  軽くサニタイズしてから使うこと。

### タスク実行中にスコープが大きすぎると判明した場合
1. その時点で完結し、動作確認できる最小の成果があれば、それだけを今回のコミット対象とする
2. 残りの作業を `docs/ROADMAP.md` の新しい子タスクとして書き出す(サイズを再見積もりする)
3. 該当タスクの status を `partial` にして理由を記載し、サイクルを終える
4. 完結した成果が無い場合は、変更を `git stash` で退避し、`blocked` と同様の扱いとする

## 3. 動作確認
- 自動テスト・lintが導入済みの場合は、それらを実行しすべて成功させてからコミットする。
- 未導入の段階では、変更した画面をブラウザで実際に操作して動作確認したことを
  コミットメッセージまたは`docs/cycle-log.md`に明記する。
- 自動テストの導入自体が価値ありそうだと感じたら、実装せず`docs/ROADMAP.md`に
  タスクとして追記するだけにする。
- 2回連続で同じ原因の不具合が解決できない場合:
  - 変更を `git stash` で退避
  - `docs/ROADMAP.md` の該当項目を `blocked` にして理由を記載
  - そのことだけをコミットしてサイクルを終える

## 4. 簡易セルフレビュー
コミット前に、まだcommitしていない差分(ワーキングツリー・新規ファイル含む)を
以下の観点で見直す。
- `docs/firestore-design.md` のスキーマ・セキュリティ方針から逸脱していないか
- `docs/screens.md` の画面構成・遷移から逸脱していないか
- モバイル幅で崩れないか

指摘があれば、その場で修正してから同じコミットに含める。
軽微・対応不要と判断したものは、対応せずサイクル終了時の報告で触れる。

## 5. ドキュメント更新
- サブタスクを `[x]` にした際は、`docs/ROADMAP.md` から該当行を削除し、
  `docs/roadmap-done.md` の対応する画面見出し欄へその場で退避する。
- ある画面のサブタスクが全て完了した場合、`docs/ROADMAP.md` 側のその画面のstatusを
  `完了` にする。
- **`完了`画面への新規タスク追加時は status を `進行中` に戻す**。

## 6. コミット・プッシュ
- 1サイクルの成果を必ず1コミットにまとめ、`evolve/cycle-<連番>` ブランチにpushする。
- コミットメッセージ形式: `feat: <内容>` / `fix: <内容>` / `docs: <内容>`

## 7. バックログ更新・サイクル終了報告
- 今回選ばなかったタスク、新たに見つけた改善点をROADMAP.mdに反映する。
- 以下の内容を `docs/cycle-log.md` に追記する:
```
## YYYY-MM-DD HH:MM
- 実装: (実装した内容)
- 動作確認: OK / 未確認箇所あり(内容)
- レビュー: OK / 指摘N件対応 / スキップ
- 次回予定: (次のサイクルで着手予定の項目)
- blocked / partial: なし or (内容)
```
追記後、同じ内容をターミナルにも表示する。

---

## 禁止事項
- mainへの直接commit/push/merge(取り込みは人間がレビュー後に行う)
- PRの作成・マージ(`gh pr create`、`gh pr merge`等)を自分で実行すること。
  取り込みの判断と実行は必ず人間が行う
- 履歴改変(`rebase -i`、force push、`reset --hard`) — evolveブランチ上でも禁止
- 動作確認していない状態でのcommit/push
- ROADMAPにない大規模リファクタリング
- ROADMAPを経由しない新規画面の追加
- `docs/firestore-design.md` のセキュリティ方針(list禁止等)を緩める実装
