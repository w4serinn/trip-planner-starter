# Firestore スキーマ設計

要件定義書(requirements.md) 9章のエンティティを、Firestoreの実際のコレクション/ドキュメント構造に落とし込む。

## 全体構造
```
groups/{groupCode}                          … グループ（合言葉がドキュメントID）
  - createdAt
  - members: string[]                        （参加時に名前を追記）

  trips/{tripId}                             … 旅行（自動ID）
    - name
    - createdAt
    - meetingPlace, meetingTime, meetingNote  （集合情報：単一の値なので旅行ドキュメントに直接持たせる）
    - warikaUrl                               （割り勘リンク：同上）
    - planningNotesText                       （企画メモ：単一の共有テキスト。2026-08-18変更、下記参照）
    - scratchText                             （雑多メモ：単一の共有テキスト。2026-08-18変更、下記参照）

    destinations/{destId}
      - name, note, addedBy, addedAt
      - votes: { [memberName]: number(1-5) }

    scheduleEntries/{date}                    （ドキュメントIDを日付 "YYYY-MM-DD" にする）
      - responses: { [memberName]: "○"|"×"|"△" }

    lodgingCandidates/{id}
      - url, note, addedBy, addedAt

    confirmedStays/{id}
      - url, note, checkIn, checkOut, addedBy

    itineraryItems/{id}
      - title, date, time(optional), locationUrl(optional), note(optional), addedBy
```

## 設計判断
- **集合情報・割り勘リンク・企画メモ・雑多メモはサブコレクションにせず、`trips/{tripId}` ドキュメントに直接フィールドとして持たせる**。
  集合情報・割り勘リンクは要件9.3で「単一の置き場」と整理した通り複数件持つ必要が無いため。
  企画メモ(`planningNotesText`)・雑多メモ(`scratchText`)はいずれも2026-08-18の変更で単一共有
  テキストになったため同様の扱いとした(下記「UI刷新に伴うデータモデル変更」参照)。
- **行き先候補・宿泊候補・確定宿泊・しおり項目は、それぞれサブコレクションにする**。
  複数件追加され、一覧表示・並び替えが必要なため。
- **日程調整(scheduleEntries)は、日付をそのままドキュメントIDにする**。
  同じ日付への複数人の同時書き込みも `responses` マップのフィールド単位更新になるため、Firestoreの
  マージ書き込み(`set({...}, {merge:true})`)で衝突しにくい。

## UI刷新に伴うデータモデル変更（確定 / 2026-08-18）
`docs/screens.md`「UI刷新方針」の通りアプリ全体をSPA化するのに合わせ、以下の2点を変更した。

- **企画メモ: `planningNotes`サブコレクション(投稿者名付き個別メモの一覧) → `trips/{tripId}.planningNotesText`(単一の共有テキストフィールド)**。
  「hackmdのように1枚にみんなで書き足していく」体験を実現するため。同時編集時の競合(後勝ち上書き)は
  許容する。旧`planningNotes`サブコレクションのデータは移行しない(現時点で開発中のテストデータのみのため)。
- **雑多メモ: `trips/{tripId}.scratchText`(単一の共有テキストフィールド)**。「まず自由に書きなぐって、
  後で企画メモ/しおりに振り分ける」というブレインダンプ用の置き場。企画メモと同じく、旅行1件につき
  1つの共有テキストにみんなで自由に書き足していく。同時編集時の競合(後勝ち上書き)は許容する。

いずれも`trips/{tripId}`配下の通常のフィールドであり、`firestore.rules`は既存の`trips/{tripId}`
ドキュメントに対する`update`権限がそのまま適用されるため、**ルール自体の変更は不要**。

## 雑多メモの振り分け方式の再設計（確定 / 2026-08-18・追加変更）
上記の通り雑多メモを単一共有テキスト化したのに伴い、「→企画メモへ」「→しおりへ」の振り分け対象を
以下のように再定義した(人間との確認の上、選択範囲移動方式に確定)。

- 振り分けは**雑多メモのテキストエリア内でユーザーが選択(ドラッグ選択)したテキスト範囲**に対して行う。
  これはテキストの範囲選択という標準的な操作であり、docs/screens.mdで不採用と決めた「ドラッグ&ドロップ
  (要素そのものを掴んで運ぶ操作)」とは別物である。選択後にボタンをタップする点は変わらないため、
  「ボタンタップ式」というUI方針自体は維持される。
- **「→企画メモへ」**: 選択範囲のテキストを`planningNotesText`の末尾に追記し、`scratchText`側は
  選択範囲のみを削除する(前後のテキストはそのまま残る)。
- **「→しおりへ」**: 選択範囲のテキストを`itineraryItems`の新規ドキュメントの`title`に設定して作成する
  (日付は別途、日付選択のみの簡易フォームを挟んで指定する。`note`等の他フィールドは空のまま)。
  作成後、`scratchText`側は選択範囲のみを削除する。
- 何も選択していない状態でボタンを押した場合はエラー表示とし、何も起きないようにする。

## セキュリティ方針（確定）
Firebase Authを使わない前提のため完全な認証は導入しないが、以下の対策を組み合わせて
「合言葉を知らない第三者が到達できない」状態を作る。

1. **`groups`コレクション直下でのみ`list`クエリを禁止し、`get`（個別ドキュメント取得）のみ許可する**。
   これにより、正確な合言葉（＝ドキュメントID）を知らない限り、グループを一覧化して
   総当たりする経路そのものを塞げる。コストはほぼゼロで効果が大きいため必須とする。
   なお`groups/{groupCode}`配下（trips以下の各サブコレクション）は、そのパスに到達する
   時点で正しい合言葉をすでに知っている必要があるため、`list`も許可してよい
   （候補地一覧・しおり一覧など、アプリの表示機能そのものがこれに依存するため）。
2. **合言葉は6〜8文字に伸ばす**（当初案の4文字から変更）。
   書き写す手間とのトレードオフだが、現実的な時間での総当たりを困難にする。
3. **Firebase App Checkを導入する**。このアプリ経由の正規リクエストであることを検証し、
   外部スクリプトからの機械的なアクセスを困難にする。無料枠内で完結する。

## App Check導入の見送り（2026-08-18 決定）
上記3の「App Check」は、実装段階で以下の問題により見送ることとした。

- 有効なApp Checkトークンをブラウザ実SDK・curl両方で送っても、Firestore側が一貫して
  `403 Missing or insufficient permissions`を返す原因不明の不整合が発生した
- コード側（初期化・トークンの中身・ヘッダー名・APIキー制限）は全て正常と確認済みだった
- 友人内利用というリスクの小ささに対して、原因調査に投じるコストが見合わないと判断した

`list`禁止・合言葉6〜8文字の2層で当面運用し、App Checkは任意の将来課題として
`docs/ROADMAP.md`の`Could`枠に残す。

**根本原因（判明済み）**：`firestore.rules`から`isAppCheckValid()`を外しても403が続いた
原因は、Firebase Console「App Check」→「API」タブでCloud Firestoreが「適用（Enforce）」
状態のままだったこと。これは`firestore.rules`のコードとは**独立したプラットフォーム層の
ゲート**であり、ルール側の設定だけでは解除できない。「適用解除（Unenforce）」に切り替えた
ことで、トークン無しでの読み書きが正常に成功するようになった。
（教訓：Firebaseのセキュリティ設定は「ルールのコード」と「Console上のプラットフォーム
設定」の2箇所に分散している場合があり、両方を確認する必要がある）

Cloud Functionsによる本格的な合言葉検証・トークン発行（＋Blazeプラン移行）は、
今回は過剰と判断し見送る。将来的に「本気で個人開発サービス化したい」となった際の
選択肢として保留する。

## 削除権限の方針（確定）
候補地・企画メモ・宿泊候補・確定宿泊・しおり項目など、`groups/{groupCode}/trips/{tripId}`
配下のサブコレクション各ドキュメントは、**合言葉を知っている人なら誰でも削除できる**。

認証を導入しない前提（要件7-1）である以上、「追加した本人だけ削除可」という制限は
技術的に作れない（名前は自己申告であり、他人の名前を騙って操作することも防げないため）。
削除を許可しないか、誰にでも許可するかの二択であり、身内の信頼関係を前提にした
このアプリ全体の設計方針と一貫性を取り、後者を採用する。

対象: `groups/{groupCode}/trips/{tripId}/{subcollection}/{docId}` の `delete`
（`groups`・`trips`自体の削除は対象外。誤操作の影響が大きいため引き続き禁止する）

## グループ作成方法の方針（確定 / 2026-08-18、2026-08-18 再検討で更新）
公開サイト(GitHub Pages)から新規グループを作成できるようにするが、**作成用の合言葉を
クライアント側コードに埋め込まない**方式にする。

- 経緯：GitHub Pagesは誰でもアクセスできるpublicなサイトのため、「既存グループへの参加」は
  合言葉が防波堤になるが、「新規グループ作成」には元々何の制限も無く、部外者でも部屋を
  量産できる状態だった。当初は「運用者のローカルスクリプト経由に一本化する」方針にしたが、
  友達グループ全員が作成できる運用の方が好ましいと判断し、以下の方式に変更した。
- **なぜコードへの直接埋め込みではダメか**：ブラウザに配信されるJSはどんな形であれ閲覧可能
  なため、`if input === "秘密の文字列"`のような比較を書くと、その文字列自体が誰でも読める
  状態になり、部外者に対する防波堤として機能しない。
- **採用する方式**：Firestoreのセキュリティルールの`get()`関数を使い、`config/adminSecret`
  という別ドキュメントに作成用合言葉を保管する。クライアントは新規グループ作成時、送信する
  データの中にこの合言葉を含める。ルール側は`get()`でこのドキュメントの値と一致するかだけを
  判定し、一致しなければ`create`を拒否する。判定結果（真偽）以外の情報はクライアントに
  一切返らないため、`config/adminSecret`の値自体はコードにも通信レスポンスにも登場しない。
- **この方式でも「友達には見つかる」ことは許容する**：作成した`groups/{code}`ドキュメントに
  合言葉の値を保存すれば、そのグループに参加した友達はデータを読めば見つけられる。
  ただし、その友達は元々合言葉を知っている＝信頼されて参加している立場であり、削除・編集も
  自由にできる今の設計と同じ信頼前提の範囲内のため、これは受容する。防ぎたいのは
  「合言葉を一切知らない部外者」による部屋の量産であり、この方式で目的は達成できる。
- **実装上の注意**：作成用合言葉の値そのものは、送信データの中に含めて保存する必要はない
  （ルール側の`get()`比較にしか使わないため）。もし友達が見つけられる状態を望まないなら
  保存しない設計も可能だが、今回は「友達なら見てもよい」の前提のため、保存する/しないは
  実装時の任意判断とする。

## ホスティング方針（確定）
GitHub Pages（publicリポジトリ）を使う。

このアプリの安全性は「秘密にすること」に依存しない設計にしてある
（list禁止・十分な桁数の合言葉という、公開されても機能する仕組みのため）。
コード自体もブラウザで動く以上デプロイ後はどのみち閲覧可能であり、Firebaseの設定値
(apiKey等)も秘匿情報ではないため、privateリポジトリにする実利は薄いと判断した。
Firestoreのセキュリティはコードやキーの秘匿ではなく、セキュリティルール
(list禁止等、上記「セキュリティ方針」参照)側で担保する。

## 未確定・要注意点
