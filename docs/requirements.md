# 旅行計画アプリ 要件定義書（ドラフト）

## 1. 背景・目的
特定の友人グループが定期的に旅行へ行く前提で、その都度の「行き先決め」「日程調整」を
同じ場所で継続的に行えるようにする。単発の投票ツールではなく、グループの旅行履歴を
積み重ねていける場を目指す。

## 2. 想定ユーザー
- 固定の友人グループ（数人〜10人程度）
- 各自スマホからアクセスして編集
- 不特定多数への公開は想定しない（グループ内利用が前提）

## 3. 利用形態
- 汎用サービスではなく、特定グループが繰り返し使う自分たち専用ツール
- 旅行の企画が持ち上がるたびに同じ場所へ集合し、行き先→日程の順で決めていく想定

## 4. 旅行企画の実際の流れ
```
① 企画（やりたいこと・テーマを出し合う）
      ↓
② 行き先決め ← ①に沿って決まる
      ↓
③ 宿を決める（決定自体はDiscord等の会話で行う）
      ↓
④ 現地で何をするか決める（しおり）
      ↓
⑤ 移動手段（各自バラバラ／合流場所以降は代表者が手配）
```
この流れに沿って機能を設計する。

## 5. スコープ

### 5.0 全体構造
グループ（固定の友人メンバー）の中に、複数の「旅行」を作成できる二階層構造とする。
以下の機能はすべて「1つの旅行」に紐づくデータとして持つ。

```
グループ
 └─ 旅行A（例：2026年夏 九州旅行）
     ├─ 企画メモ（やりたいこと出し）
     ├─ 行き先決め
     ├─ 日程調整
     ├─ しおり
     ├─ 宿泊候補（Airbnbリンク＋メモ）／確定ホテルリンク
     ├─ 集合場所・時間の共有
     └─ 割り勘リンク（Walica）
 └─ 旅行B
     └─ ...
```

### 5.1 機能一覧・優先度（MoSCoW）
| 機能 | 内容 | 優先度 |
|---|---|---|
| グループ参加 | 名前＋合言葉でグループに入る | Must |
| 旅行の作成・一覧 | グループ内で「旅行」を新規作成し、過去分も一覧から見返せる | Must |
| 企画メモ | しおりとは別に、旅行が固まる前の「やりたいこと」をみんなで自由に書き溜める、単一の共有メモ欄 | Must |
| 行き先決め | 候補地を追加し、★等で投票・ランキング表示 | Must |
| 日程調整 | 参加者が行ける日を日単位の○×△で入力し合うアンケート | Must |
| 宿泊候補管理 | Airbnb等の候補リンクを貼り、メモを添えて比較できる置き場（投票機能なし、決定は口頭・Discord） | Must |
| 確定ホテル置き場 | 最終的に泊まる宿のリンクを1箇所に固定表示 | Should |
| 割り勘リンク置き場 | 外部サービス「Walica」(walica.jp)の精算リンクを貼るだけの置き場 | Should |
| 旅のしおり | 現地で何をするかを書き貯める共同メモ／リスト | Should |
| 集合場所・時間の共有 | 合流場所・時間を旅行ごとに1箇所へ記載しておく欄 | Should |
| 通知・リマインド | 入力があったことを知らせる等 | Could |
| 参加者の簡易パスワード等 | なりすまし対策 | Won't（今回は不要と明言済み） |
| 交通手段の予約調整機能 | 各自バラバラに手配するため、アプリ側での調整は不要 | Won't |

（2026-08-20追記）上記「交通手段の予約調整機能」のWon't判断は、予約・手配の
調整をアプリ側で行わないことを指しており、しおり項目に「電車で移動」等の
移動手段を一言メモする軽微な入力欄（下記9.1「しおり項目」参照）を追加することとは
別物と整理した。実際に使ってみて「しおり項目に目的地までの移動手段を書く場所が
ない」という不便さが見つかり、単なるメモ欄として`docs/ROADMAP.md`「61」で追加した
（予約調整・比較・手配のような機能は引き続きWont のまま）。

## 6. 非機能要件
- **永続性**：長期保存前提。ページを閉じても消えない、数ヶ月後でも見返せる
- **同時編集**：複数人がほぼ同時にアクセス・編集する前提（正確なリアルタイム同期までは不要、数秒〜十数秒の反映遅延は許容）
- **プラットフォーム**：モバイルブラウザ中心、レスポンシブ対応
- **認証**：簡易的な識別のみ想定（本格的なアカウント管理は不要という前提。要確認）

## 7. 確定事項
1. **グループの参加管理**：合言葉のみで参加可能。なりすまし対策・パスワードは不要（身内の仲間内利用のため）
2. **日程調整の粒度**：日単位の○×△カレンダー形式
3. **宿泊候補（Airbnb）の決め方**：アプリ側では投票機能を持たない。候補リンク＋メモを並べる「一覧・比較」までが役割で、最終決定はDiscord等のボイスチャットで会話しながら行う想定
4. **企画メモ**：しおりとは別建ての、企画段階専用の自由記述メモ欄として持つ
5. **移動手段の情報共有**：集合場所・時間の共有のみで十分。チケット等のリンク置き場は不要
6. **旅行のステータス管理**：企画中／確定／完了のような進行段階は持たせない
7. **通知・リマインド**：実装しない（LINE等の既存連絡手段で完結）
8. **しおりの形式**：日付でグルーピングし、各日の中は時間目安（任意入力）で自動時系列ソート。項目は「やること名」必須、「時間目安」「場所リンク」は任意

## 8. 未確定の論点
現時点でなし。要件定義はここで一区切りとする。

## 9. 用語定義・データモデル

### 9.1 エンティティ一覧
| エンティティ | 説明 |
|---|---|
| グループ (Group) | 固定の友人メンバーの集まり。合言葉で識別 |
| メンバー (Member) | グループの参加者。IDは持たず「名前」で識別する（要件7-1の通り認証なし） |
| 旅行 (Trip) | グループ内で作られる1回分の旅行企画。すべての下位データの親 |
| 企画メモ (PlanningNote) | 旅行が固まる前の「やりたいこと」の書き溜め。旅行につき1件の共有テキスト（2026-08-18改訂。旧: 投稿者名付き複数件の一覧） |
| 雑多メモ (ScratchNote) | まず自由に書きなぐるブレインダンプ欄。旅行につき1件の共有テキスト（2026-08-18改訂。旧: 投稿者名付き複数件の一覧）。選択したテキスト範囲を「→企画メモへ」「→行き先決めへ」「→しおりへ」「→宿泊へ」でコピーして他タブへ振り分けられる（2026-08-19振り分け先拡張、2026-08-20カットからコピーに変更） |
| 行き先候補 (DestinationCandidate) | 候補地名・メモ・投票（メンバー名→★スコア） |
| 日程候補 (ScheduleEntry) | 日付ごとに、メンバー名→○×△の回答を持つ |
| 宿泊候補 (LodgingCandidate) | Airbnb等のURL・メモ・追加者名（投票なし） |
| 確定宿泊 (ConfirmedStay) | 実際に泊まる宿1件分。URL・メモに加え、チェックイン〜チェックアウトの期間を持つ。旅行内で複数件持てる（連続しない日程の分割も可） |
| しおり項目 (ItineraryItem) | やること名（必須）・日付・時間目安（任意）・場所リンク（任意）・移動手段（任意、2026-08-20追加）・メモ（任意）を持つ。日付でグルーピングし、各日の中は時間目安の早い順に自動整列する |
| 集合情報 (MeetingInfo) | 旅行につき1件、集合場所・時間 |
| 割り勘リンク (WalicaLink) | 旅行につき1件、Walica(walica.jp)のURL |

### 9.2 関係
```
Group 1 ── N Trip
Group 1 ── N Member（合言葉参加時に追加される名前の一覧）

Trip 1 ── N DestinationCandidate ── N 票（Member名をキーにしたスコア）
Trip 1 ── N ScheduleEntry ── N 回答（Member名をキーにした○×△）
Trip 1 ── N LodgingCandidate
Trip 1 ── N ConfirmedStay（各件が宿泊期間を持つ。0件〜複数件、日程が飛び飛びでもよい）
Trip 1 ── N ItineraryItem
Trip 1 ── 1 PlanningNote（単一の共有テキスト。2026-08-18改訂）
Trip 1 ── 1 ScratchNote（単一の共有テキスト。2026-08-18改訂）
Trip 1 ── 1 MeetingInfo（0 or 1）
Trip 1 ── 1 WalicaLink（0 or 1）
```

### 9.3 設計メモ
- メンバーは独立エンティティというより「グループが持つ名前のリスト」に近い扱いでよい（名前の重複や認証は要件7-1により考慮不要）
- 投票・回答系（行き先の★、日程の○×△）は「メンバー名→値」のマップとして各候補に持たせる形で表現できる
- **「単一の置き場」なのは集合情報・割り勘リンク・企画メモ・雑多メモ**（企画メモは2026-08-18改訂で追加、雑多メモも同日の追加変更で個別メモの一覧から単一共有テキストへ変更）。確定宿泊は当初「旅行につき1件」としていたが、予約が取れず複数の宿に分かれるケースがよくあるため、行き先候補や企画メモと同じ「複数追加できるリスト」に修正した。各件は宿泊期間（チェックイン〜チェックアウト）を持ち、区間が連続している必要はない
- **宿泊候補には期間を持たせない**。候補出しの段階ではまだ日程が固まっていないため、期間は確定宿泊（ConfirmedStay）になった時点で初めて紐づける

## 10. 受け入れ条件（Definition of Done）

### 10.1 機能ごとの受け入れ条件（Must機能）
| 機能 | 完了とみなす条件 |
|---|---|
| グループ参加 | 合言葉を知っている人なら誰でも、名前を入力してグループに入れる。既存メンバーとして再度参加しても状態が壊れない |
| 旅行の作成・一覧 | グループ内に複数の旅行を作成でき、過去に作った旅行も一覧から開いて中身を見返せる |
| 企画メモ | 旅行につき1枚の共有テキストに、誰でも自由に書き足せる（2026-08-18改訂） |
| 行き先決め | 候補地を追加でき、★でメンバーごとに投票でき、平均スコアでランキング表示される |
| 日程調整 | カレンダー上で日付ごとに○×△を入力でき、メンバー全員の回答が一覧で見える |
| 宿泊候補管理 | Airbnb等のURLとメモを追加・一覧表示でき、投票機能がないことが明確なUIになっている |
| 確定宿泊 | 宿泊期間（チェックイン〜チェックアウト）付きで複数件登録・一覧表示でき、日程が飛び飛びでも表示が破綻しない |

### 10.2 MVP全体の完成条件
以下の一連の流れを、1つの旅行に対して最初から最後まで実際に操作できること。
```
グループに参加 → 旅行を新規作成 → 企画メモを書く → 行き先に投票する
→ 日程に○×△で回答する → 宿泊候補を並べて比較する → 確定宿泊を複数登録する
```
複数人（最低2名分の名前）でそれぞれ操作し、互いの入力がお互いから見える状態になっていること。
