# ROADMAP

## 進め方の方針
- タスクはこの順で上から着手する: `0. 基盤` → Must機能(1〜6) → Should機能(7〜9)
- `0. 基盤`が完了するまで、他のセクションには着手しない(全機能がFirestore接続と
  画面シェルに依存するため)
- 1サイクル = 意味的にまとまった単位(目安: S/Mサイズ1〜3個)。詳細な1周の手順は
  `.claude/skills/evolve/SKILL.md`を参照
- サイズ目安: S = 数十行程度の変更、M = 1画面の主要機能一式

## 第3期: レイアウト刷新

`16`でトークン(配色・角丸等)は変更したが、人間から「レイアウトも汚い」との評価を受け、
2026-08-19に人間とのチャットで追加方針を決定。トークンいじりだけでなく、各画面のHTML
構造・CSSを作り直すレベルまで踏み込む(データモデル・Firestore構造・`docs/screens.md`の
画面構成・遷移は不変。あくまで既存画面の内部レイアウト・視覚表現の作り直し)。

背景・調査結果:
- 「安っぽく見える」の主因は、絵文字的な装飾の不足ではなく、①SVGアイコンが無い
  ②タイポグラフィに階層が無い ③余白のリズムが均一 ④画面ごとの表情が全部同じ
  (どのタブも「見出し→フォーム→リスト」の判で押した構成) ⑤状態変化にトランジションが
  無く一瞬で切り替わる、の5点と分析した。
- Wanderlog(旅行プランナー)・TimeTree(共有カレンダー)等の既存アプリを調査し、
  「追加フォームを常時表示せず折りたたむ」「一覧をカード/タイムライン的に見せる」等の
  パターンを参考にした。絵文字によるアイコン代用は不採用(OS/ブラウザで見た目が
  バラバラになり、狙いと逆に安っぽく見えるリスクがあるため)。

## 第5期: 配色・タイポグラフィの統一感強化

2026-08-19、人間から「デザインがまだ単調」との指摘を受け、複数の参考サイト
(sankoudesign.com「旅行・観光」カテゴリ、w4serinn.github.io/yamagata_trip、
miricanvas「旅のしおり」テンプレート、design-library.jp「お問い合わせ」UI集、
g-mark.org受賞ギャラリー)を調査した上で方針を確定。「和風」等の特定スタイルへの
転換ではなく、**既存の明るい青ベース配色を活かしつつ、体系立った統一感を持たせる**
方向で合意(配色の全取っ替えは4回目になるため、既存資産を活かす)。

背景・調査結果:
- yamagata_tripの実CSSを直接確認したところ、フォントペアリング・伝統色による
  体系的な配色・CSSのみのテクスチャ(画像不使用)・番号バッジ・全面塗りセクションに
  よるリズムづけが、写真無しでも「単調に見えない」ことに効いていると判明
- design-library.jp自体のCSSから、ピル型ボタン(`border-radius:50px`、
  パディング`9-10px 14-16px`)・青みを帯びたカード影(`rgba(0,0,128,...)`系)の
  具体的な数値を採取
- miricanvasの「旅のしおり」テンプレートは「ベース+アクセント2〜3色に絞る」
  「情報をブロックごとに枠線で区切る」という、既存のカード主体の設計と親和性の高い
  方針を採用している
- g-mark.orgの受賞デザイン(id:14776)は「AIカレンダー/日程調整ツール」という
  同カテゴリの製品だったが、JS描画のため詳細は自動取得できず、人間が直接確認したい
  場合は別途ブラウザで見る必要がある

`23. デザイントークンの拡充`は完了済み(詳細はdocs/roadmap-done.md参照)。
Zen Kaku Gothic New採用・`--color-primary-deep`/`--color-accent-green`追加・
青みを帯びた`--shadow-card`・`--radius-pill`追加と`.rank-badge`への適用まで完了。

### 27. カスタムカレンダーピッカーの導入(複数選択対応)
2026-08-19、jicoo.com(日程調整ツール)を参考に人間から提案。現状の`<input type="date">`は
ブラウザ標準のUIで、見た目に一貫性が無い。F(日程調整)画面から着手し、独自にスタイリングした
カレンダー形式の日付選択コンポーネントに置き換える(格子状のピル型ボタンで日付/時間帯を
選ぶ、というjicoo.comのUIパターンを参考にしつつ、このアプリの実際のデータ構造に合わせて
調整する)。加えて人間から、**F画面では複数日をまとめて選択・追加できるようにして操作性を
上げてほしい**との要望あり(候補日を1件ずつ「開く→選ぶ→送信」を繰り返す手間を無くす)。
保存するデータ形式(`scheduleEntries/{date}`、1ドキュメント=1日付という構造)自体は
変えない(しおりの時間入力をプルダウン化した`15`と同じ考え方。複数選択時も、選択された
日付ごとに`setDocumentMerged`を呼ぶだけで、Firestoreスキーマ・書き込み方式は据え置き)。
CSSだけでは完結せず、月めくり・日付グリッド描画・複数選択状態の管理等のJSロジックが
新たに必要になる規模のため、Lサイズとして以下に分割する。
`27. カスタムカレンダーピッカーの導入`は完了済み(詳細はdocs/roadmap-done.md参照)。
`src/datePicker.js`(単一・複数選択モード対応)を新規作成し、F(日程調整)の「候補日を
追加」(複数選択モード)、G(宿泊)の確定宿泊チェックイン/チェックアウト・H(しおり)の
日付(いずれも単一選択モード)に適用した。既存の`<input type="date">`はF/G/Hから
すべて置き換わった。

第5期のタスクは以上で全て完了。

      判断する(`26`の実装メモに倣い、対象・方向性は実装時の裁量とする)
